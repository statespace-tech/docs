Statespace runs only builds that your CI recorded. This guide records builds from GitHub Actions.

## Kinds of build

A build is an image or a folder of files. The runtime of your app tells you which kind to record.

| Build | Input | Runtimes |
| --- | --- | --- |
| An image, by digest | `image` | Docker, Kubernetes, Cloud Run, ECS Fargate, Fly.io |
| A folder of files in a bucket | `files` | S3, Cloud Storage |

Each runtime uses only its own kind. One commit, folder, and label holds one build. So an image build and a files build of one commit need different `app` labels. See [Build labels](#build-labels).

## Build every push

Build each commit that can become an arm. The simplest way is to build each push to each branch.

  <Tab title="Image">
    The workflow builds the image, pushes it, and records it by digest.

    <BuildWorkflow />
  </Tab>
  <Tab title="Files">
    The workflow builds the site, uploads the files to a folder for the commit, and records the folder. Both lines name the full location.

    <BuildWorkflowFiles />

    You choose the folder. Statespace has no rule for its name. For Cloud Storage, see [Cloud Storage](/guides/gcs#record-each-build).
  </Tab>
</Tabs>

To build fewer commits, use a branch pattern, such as `branches: ["main", "try/**"]`. A branch name means nothing to Statespace. Only the build record counts.

The job needs `id-token: write`. The action sends the job's GitHub OIDC token, and Statespace gets the repo and the commit from it. CI keeps no Statespace secret.

Statespace finds the live commit from the build that live runs. So the workflow that deploys live must record that build too. Add the action step to that workflow.

## Checks of the build

The action checks that the build exists before it records it. When a check fails, the step fails, and Statespace records nothing.

- **Image.** The registry must have the image, by digest. The action checks it with `docker manifest inspect`. A wrong repository fails the step.
- **Files.** The action lists the folder, downloads the files, and computes a hash of them. An empty folder, or a folder that the job cannot read, fails the step.

So the job needs read access to the image or the folder. The credentials that pushed the build give this access.

## Inputs

Give exactly one of `image` and `files`.

<ParamField body="image" type="string">
  The image, by digest, such as `ghcr.io/acme/shop@sha256:2222…`. The action resolves a tag to its digest with `docker`.
</ParamField>

<ParamField body="files" type="string">
  The folder of the files, as `s3://<bucket>/<folder>/` or `gs://<bucket>/<folder>/`, such as `s3://acme-site/builds/a1b2c3d…/`. It ends with `/`. It cannot be the root of the bucket: the root holds live.
</ParamField>

<ParamField body="path" type="string">
  The folder of `statespace.toml`, from the root of the repo, such as `.` or `services/shop`.
</ParamField>

<ParamField body="app" type="string">
  The app that this build is for. Without it, the build serves every app of the repo and folder. See [Build labels](#build-labels).
</ParamField>

## Checks of statespace.toml

The action sends `statespace.toml` with the build. Statespace checks the file.

- A wrong key, a wrong type, or a CEL error fails the step, with the message.
- A section `[app.<name>]` that matches no app gives a warning. The step does not fail.

So a commit with a bad file gets no build, and cannot become an arm.

## Build labels

Some builds put different values in the build for each app. For example, a web app can put its API address in the bundle at build time. Then make one build for each app, and give each build its app. This example builds images. A folder of files takes `app` in the same way.

```yaml .github/workflows/build.yml
jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - app: shop-dev
            api: https://api.dev.acme.com
          - app: shop-prod
            api: https://api.acme.com
    steps:
      # Check out, and sign in to the registry, as above.
      - uses: docker/build-push-action@v6
        id: build
        with:
          context: .
          push: true
          build-args: API_URL=${{ matrix.api }}
          tags: >-
            ghcr.io/acme/shop:${{ matrix.app }}-${{ github.sha }}
      - uses: statespace-tech/action@v1
        with:
          image: >-
            ghcr.io/acme/shop@${{ steps.build.outputs.digest }}
          path: .
          app: ${{ matrix.app }}
```

These rules choose the build of a commit for an app:

1. A build with `app: shop-prod` serves only `shop-prod`.
2. For `shop-prod`, a build with `app: shop-prod` wins over a build without `app`.
3. A build without `app` serves every app of the repo and folder.

Two builds of one commit and folder without `app` must be the same: the same image, or the same files. The same build again is accepted. A different build fails with this message:

```text
a1b2c3d has a build without app already. Add app: so
Statespace knows which build is for which app
```

`ssp experiment update` prints the build that it chose for each arm.
