Use `ssp proxy gcs` for a static site in a Cloud Storage bucket. The proxy serves the files of the bucket, like a static website endpoint. Each subject can get a different build.

```text
                        ┌─► gs://acme-site/                 (live)
visitors ─► site-proxy ─┼─► gs://acme-site/builds/c0ffee1…/
                        └─► gs://acme-site/builds/a1b2c3d…/
```

## How it works

<Planned />

- CI uploads the files of each commit to a folder, such as `builds/<commit>/`. Then it records the folder with `statespace-tech/action@v1`.
- Live is the files at the root of the bucket, without the build folders.
- An arm is the build folder of its commit. The proxy serves the files of that folder to the subjects of the arm.
- The proxy only reads. It never writes to the bucket, and it never copies files.
- The proxy counts the visitors and the events of the arms, as on every runtime.
- An arm has no process, so it gets no environment or request headers. The cookie `ssp_arms` labels its visitors for browser analytics. See [Find it in your own tools](/guides/own-tools#browser-analytics).
- The proxy uses the Cloud Storage JSON API with Google credentials: the metadata server, or Application Default Credentials, such as a user, a service account key, or workload identity federation. It uses no HMAC keys.

## Prerequisites

- A static site in the repo `acme/site` that builds its files to `dist/`.
- The Cloud Storage bucket `acme-site` in the project `acme-web`.
- An app, such as `site-prod`.
- A Workload Identity Federation provider for GitHub Actions, and the service account `site-ci` that CI uses.
- A container service near the bucket for the proxy. See [Where to run the proxy](#where-to-run-the-proxy).
- The proxy image `ghcr.io/statespace-tech/statespace:0.5.0`, in a registry that your container service can use.

## Record each build

This workflow builds each push to each branch. It uploads the files to a folder for the commit, and records the folder. Both lines name the full location.

```yaml .github/workflows/build.yml
# Build each push to each branch, upload the files,
# and record the build.
name: Build
on:
  push:
    branches: ["**"]
permissions:
  contents: read
  # Google Cloud and the Statespace action use OIDC.
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: npm ci && npm run build
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: <provider>
          service_account: >-
            site-ci@acme-web.iam.gserviceaccount.com
      - uses: google-github-actions/setup-gcloud@v2
      # Upload the files of this commit to its own folder.
      - run: >-
          gcloud storage rsync dist/
          gs://acme-site/builds/${{ github.sha }}/
          --recursive
      # Record the folder. Keep this step after the upload.
      - uses: statespace-tech/action@v1
        with:
          files: gs://acme-site/builds/${{ github.sha }}/
          path: .
```

You choose the folder. Statespace has no rule for its name. Put all builds in one folder, such as `builds/`. See [How Statespace finds live](#how-statespace-finds-live).

The action lists the folder, downloads the files, and computes their files hash. An empty folder, or a folder that the job cannot read, fails the step. So give `site-ci` the role Storage Object Admin on the bucket. It uploads, reads, and lists.

```shell
ci=site-ci@acme-web.iam.gserviceaccount.com
gcloud storage buckets add-iam-policy-binding \
  gs://acme-site \
  --member "serviceAccount:$ci" \
  --role roles/storage.objectAdmin
```

## Deploy live

The deploy of live records its build too. It uploads the files to the folder of the commit, and records the folder. Then it copies the folder to the root of the bucket.

```yaml .github/workflows/deploy.yml
# Deploy main to live, and record its build.
name: Deploy
on:
  push:
    branches: ["main"]
permissions:
  contents: read
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: npm ci && npm run build
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: <provider>
          service_account: >-
            site-ci@acme-web.iam.gserviceaccount.com
      - uses: google-github-actions/setup-gcloud@v2
      - run: >-
          gcloud storage rsync dist/
          gs://acme-site/builds/${{ github.sha }}/
          --recursive
      - uses: statespace-tech/action@v1
        with:
          files: gs://acme-site/builds/${{ github.sha }}/
          path: .
      # Copy the build to the root. Keep builds/.
      - run: >-
          gcloud storage rsync
          gs://acme-site/builds/${{ github.sha }}/
          gs://acme-site/
          --recursive
          --delete-unmatched-destination-objects
          --exclude 'builds/.*'
```

`--exclude` takes a Python regular expression. It matches the path relative to the source and to the destination. So `rsync` does not copy, and does not delete, objects under `builds/`. See [Infrastructure as code](/guides/infrastructure-as-code).

<Warning>
  A deploy that deletes unknown files, such as `--delete-unmatched-destination-objects` without `--exclude 'builds/.*'`, deletes the builds. Then the subjects of the arms get live.
</Warning>

## Set up the proxy

The proxy asks Statespace which app its runtime token is for.

In the commands, the proxy runs on Cloud Run in `us-east1`.

<Steps>
  <Step title="Add a service account for the proxy">
    Add the account, and keep its address in a variable.

    ```shell
    gcloud iam service-accounts create site-proxy \
      --project acme-web
    proxy=site-proxy@acme-web.iam.gserviceaccount.com
    ```
  </Step>

  <Step title="Let the proxy read the bucket">
    Give the proxy's account Storage Object Viewer on the bucket. The proxy only reads and lists.

    ```shell
    gcloud storage buckets add-iam-policy-binding \
      gs://acme-site \
      --member "serviceAccount:$proxy" \
      --role roles/storage.objectViewer
    ```
  </Step>

  <Step title="Keep the token in Secret Manager">
    Add a runtime token for the app. Put the secret in Secret Manager.

    ```shell
    ssp token add --app site-prod --note "Cloud Storage proxy"
    printf '%s' '<secret>' | gcloud secrets create \
      site-statespace-token --data-file=-
    ```

    Let the proxy's account read the secret.

    ```shell
    gcloud secrets add-iam-policy-binding \
      site-statespace-token \
      --member "serviceAccount:$proxy" \
      --role roles/secretmanager.secretAccessor
    ```
  </Step>

  <Step title="Deploy the proxy">
    Deploy the proxy as the service `site-proxy`. Use the path of the proxy image in your registry.

    The proxy works between requests: it renews its lease, checks the builds, and sends the data for the results. Thus it needs CPU that is always allocated and one instance at minimum.

    ```shell
    gcloud run deploy site-proxy \
      --region us-east1 \
      --image <registry>/statespace-tech/statespace:0.5.0 \
      --service-account "$proxy" \
      --set-secrets STATESPACE_TOKEN=site-statespace-token:latest \
      --no-cpu-throttling --min-instances 1 \
      --args=proxy,gcs,--bucket,acme-site,--cache \
      --allow-unauthenticated
    ```

    The command runs `ssp proxy gcs --bucket acme-site --cache`. The proxy asks Statespace which app its runtime token is for. For a single-page app, add `--fallback`. See [Single-page apps](#single-page-apps).
  </Step>

  <Step title="Send traffic to the proxy">
    Point your domain, such as `site.acme.com`, to `site-proxy`, not to the bucket. To put a CDN in front of the proxy, see [Behind a CDN](/guides/cdn). Then check the app.

    ```shell
    ssp app show site-prod
    ```

    The output shows the live commit, the proxy instances, and the orchestrator `gcs`.
  </Step>
</Steps>

## Where to run the proxy

Run the proxy in any container service near the bucket, such as in the same region. The proxy reads the bucket for each request that is not in its cache. So a long distance makes each response slower.

- **Cloud Run**, as in the steps above.
- **Kubernetes**, such as GKE with Workload Identity for the proxy's account.
- **ECS Fargate**, behind an Application Load Balancer, with application default credentials for Google Cloud.

The proxy works between requests. So keep at least one instance running, with CPU that is always allocated.
