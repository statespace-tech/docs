On Cloud Run, the proxy runs as its own service in front of your service. Each arm runs as its own Cloud Run service: a copy of your service with another image. The proxy never changes your service.

```text
                        ┌─► shop                           (live)
visitors ─► shop-proxy ─┼─► shop-ssp-checkout-c0ffee1…     (arm)
                        └─► shop-ssp-checkout-a1b2c3d…     (arm)
```

## How it works

- Live is the URL of your service. The live image is the image of the revision that gets the most traffic.
- For each arm, the proxy makes the service `<service>-ssp-<experiment>-<commit 12>`, such as `shop-ssp-checkout-a1b2c3d4e5f6`. It is in the project and the region of your service.
- A name has at most 49 characters. A longer name ends with a short hash. The labels `statespace-app`, `statespace-experiment`, and `statespace-commit` keep the full values.
- The service of an arm is a copy of the template of your service. Only the image changes. The copy keeps the containers, the environment, the resources, the service account, the VPC access, the scaling, the timeout, and the execution environment.
- It also gets the ingress, the launch stage, the Binary Authorization policy, and the labels of your service. It gets no variable that starts with `STATESPACE_`.
- It gets no traffic split, no custom domain, and no IAM policy of your service. Only the proxy's service account can call it: the proxy gives itself Cloud Run Invoker on it.
- The proxy sends requests to the URL of the arm's service. It puts a Google ID token for that URL in the header `X-Serverless-Authorization`, so your app keeps its own `Authorization` header.
- The proxy reads the output of the arms from Cloud Logging, with one query for all arms every 5 seconds.
- The proxy uses the Cloud Run Admin API v2, with the service account of its own Cloud Run service.
- An arm is ready when its service is `Ready`, serves its latest revision, and runs the image of the arm.
- When an experiment stops, the proxy deletes the services of its arms.

Your deploy workflow does not change. Deploy a new live with `gcloud run deploy`, Terraform, or any other tool. The proxy changes nothing in your service, so your tool sees no difference. See [Infrastructure as code](/guides/infrastructure-as-code).

<Note>
  The service of an arm has the ingress of your service. The proxy must be able to reach both, such as through the same VPC when the ingress is internal.
</Note>

## Prerequisites

- Your service on Cloud Run, such as `shop` in `us-east1`, with its runtime service account `shop-runtime`.
- The images that CI records, in a registry that Cloud Run can use, such as the Artifact Registry repository `shop` in `us-east1`.
- An app, such as `shop-prod`, and a recorded build of the image that live runs.
- The `gcloud` CLI with rights to manage the project.
- The proxy image `ghcr.io/statespace-tech/statespace:0.4.3` in a registry that Cloud Run can use.

## Set up the proxy

In the commands, `acme-shop` is the project.

<Steps>
  <Step title="Add a service account for the proxy">
    Add the account, and keep its address in a variable.

    ```shell
    gcloud iam service-accounts create shop-proxy \
      --project acme-shop
    proxy=shop-proxy@acme-shop.iam.gserviceaccount.com
    ```
  </Step>

  <Step title="Add a role for the proxy">
    Add a custom role with only the permissions that the proxy needs. With them, it makes, reads, and deletes the services of the arms, and calls your service and the arms.

    ```shell
    gcloud iam roles create statespaceProxy \
      --project acme-shop \
      --title "Statespace proxy" \
      --permissions=run.services.create,\
run.services.delete,run.services.get,\
run.services.list,run.services.getIamPolicy,\
run.services.setIamPolicy,run.revisions.get,\
run.operations.get,run.routes.invoke
    ```

    Give the role to the proxy's account on the project.

    ```shell
    gcloud projects add-iam-policy-binding acme-shop \
      --member "serviceAccount:$proxy" \
      --role projects/acme-shop/roles/statespaceProxy
    ```
  </Step>

  <Step title="Let the arms run as your service">
    Let the proxy's account act as the runtime account of your service. The services of the arms run as that account.

    ```shell
    gcloud iam service-accounts add-iam-policy-binding \
      shop-runtime@acme-shop.iam.gserviceaccount.com \
      --member "serviceAccount:$proxy" \
      --role roles/iam.serviceAccountUser
    ```

    Give it Artifact Registry Reader on the repository of the images. Cloud Run deploys an image only when the caller can read it.

    ```shell
    gcloud artifacts repositories add-iam-policy-binding shop \
      --location us-east1 \
      --member "serviceAccount:$proxy" \
      --role roles/artifactregistry.reader
    ```
  </Step>

  <Step title="Let the proxy read the output of the arms">
    Give the proxy's account Logs Viewer on the project.

    ```shell
    gcloud projects add-iam-policy-binding acme-shop \
      --member "serviceAccount:$proxy" \
      --role roles/logging.viewer
    ```
  </Step>

  <Step title="Keep the token in Secret Manager">
    Add a runtime token for the app. Put the secret in Secret Manager.

    ```shell
    ssp token add --app shop-prod --note "Cloud Run proxy"
    printf '%s' '<secret>' | gcloud secrets create \
      shop-statespace-token --data-file=-
    ```

    Let the proxy's account read the secret.

    ```shell
    gcloud secrets add-iam-policy-binding \
      shop-statespace-token \
      --member "serviceAccount:$proxy" \
      --role roles/secretmanager.secretAccessor
    ```
  </Step>

  <Step title="Deploy the proxy">
    Deploy the proxy as the service `shop-proxy`. Use the path of the proxy image in your registry.

    The proxy works between requests: it renews its lease, starts and stops arms, and sends records. Thus it needs CPU that is always allocated and one instance at minimum.

    ```shell
    gcloud run deploy shop-proxy \
      --region us-east1 \
      --image <registry>/statespace-tech/statespace:0.4.3 \
      --service-account "$proxy" \
      --set-secrets STATESPACE_TOKEN=shop-statespace-token:latest \
      --no-cpu-throttling --min-instances 1 \
      --args=proxy,cloudrun,--service,shop,--region,us-east1 \
      --allow-unauthenticated
    ```
  </Step>

  <Step title="Send traffic to the proxy">
    Point your domain, such as `shop.acme.com`, to `shop-proxy`. Then check the app.

    ```shell
    ssp app show shop-prod
    ```

    The output shows live, the proxy instances, and the orchestrator `cloudrun`.

    Your service keeps its own URL. So a load balancer in front of the proxy can send traffic to `shop` when the proxy is down. See [Fall back to live](/guides/fall-back-to-live).
  </Step>
</Steps>

## Many instances

Cloud Run can run many instances of the proxy. Every instance routes requests. Only the instance that holds the app's lease makes and deletes the services of the arms. When that instance stops, another instance gets the lease in about 30 seconds.

All instances must report the same settings and the same live image. While they do not, no experiment of the app can start, the running ones send their requests to live, and `ssp app show` says why.
