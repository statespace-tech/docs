For a static site on CloudFront and S3, two CloudFront Functions assign
each request at the edge. `ssp proxy cloudfront` keeps them current. It is
never in the request path: when it stops, the site and the arms continue
to work.

```text
                    ┌─► s3://shop-prod-site/        (live)
visitors ─► edge ───┼─► .../arms/c0ffee1…/          (checkout)
  functions         └─► .../arms/a1b2c3d…/          (checkout)
```

## How it works

- A build is an OCI image, as for every runtime. The image of a static site
  holds only its files, such as `FROM scratch` and `COPY dist/ /`.
- Live is the files at the root of the bucket. `ssp` finds the recent build
  whose image has the same files. It compares the S3 ETags with the files of
  the image. When an ETag is not an MD5, `ssp` reads and hashes the file.
- When an experiment starts, `ssp` copies the files of each arm's image to
  `s3://<bucket>/arms/<commit>/`. An arm is ready when its copy is complete.
  When the copy fails, the arm is not ready, and the start fails.
- `ssp` makes the two functions from the `subject` and `eligibility` rules
  of `statespace.toml`, and publishes them. It writes the arms and their
  shares to a CloudFront KeyValueStore. The functions read the store.
- The viewer-request function assigns the request with the same hash as
  the proxy. For a subject of an arm, it puts `/arms/<commit>` in front of
  the path. The viewer-response function sets the cookies.
- A new visitor gets the cookie `ssp_sid` from the first response. The
  visitor is in the experiment from the first page.
- CloudFront sends a real-time log of the requests to a Kinesis data
  stream. `ssp` reads the stream and records the requests of the arms.
- `ssp` never changes your distribution. You attach the functions and the
  real-time log one time.

## Prerequisites

- A static site in the S3 bucket `shop-prod-site`, behind the CloudFront
  distribution `E2EXAMPLE`, in `us-east-1`.
- An app, such as `shop-prod`, and a GitHub workflow that builds the site.
- The AWS CLI, with rights to deploy a CloudFormation stack with IAM roles.
- A VPC with a public subnet for the `ssp` service.

## Set up the runtime

<Steps>
  <Step title="Build an image of the site's files">
    Add a Dockerfile that holds only the build output.

    ```dockerfile Dockerfile.site
    FROM scratch
    COPY dist/ /
    ```

    Build and push this image in CI, and record it with
    `statespace-tech/action@v1`. See
    [GitHub Actions](/guides/github-actions).
  </Step>

  <Step title="Deploy the same files to the bucket">
    Deploy the files of the image to the root of the bucket. Keep the
    `arms/` folder: it holds the files of the arms.

    ```shell
    aws s3 sync dist/ s3://shop-prod-site/ \
      --delete --exclude 'arms/*'
    ```

    <Warning>
      A deploy that deletes unknown files, such as `aws s3 sync --delete`
      without `--exclude 'arms/*'`, deletes the arms. Their subjects then
      get errors.
    </Warning>
  </Step>

  <Step title="Keep the token in Secrets Manager">
    Add a runtime token for the app. Put the secret in Secrets Manager.

    ```shell
    ssp token add --app shop-prod --note "CloudFront"
    aws secretsmanager create-secret \
      --name shop-prod-statespace-token \
      --secret-string '<secret>'
    ```
  </Step>

  <Step title="Deploy the template">
    Deploy `deploy/cloudfront/template.yaml` of the
    [CLI repository](https://github.com/statespace-tech/statespace).
    It makes the KeyValueStore, the two functions, the Kinesis stream, the
    real-time log configuration, an IAM role, and an ECS Fargate service
    that runs `ssp proxy cloudfront`.

    ```shell
    aws cloudformation deploy \
      --stack-name shop-prod-statespace \
      --template-file template.yaml \
      --capabilities CAPABILITY_IAM \
      --parameter-overrides \
        AppName=shop-prod \
        DistributionId=E2EXAMPLE \
        BucketName=shop-prod-site \
        TokenSecretArn=<secret ARN> \
        Image=ghcr.io/statespace-tech/statespace:0.4.1 \
        VpcId=vpc-0aaa \
        Subnets=subnet-0bbb,subnet-0ccc
    ```

    The service has 0.25 vCPU and 0.5 GB, a public IP address, and no load
    balancer. It needs no NAT gateway.
  </Step>

  <Step title="Attach the functions and the real-time log">
    In the distribution, edit each cache behavior:

    1. Set the viewer-request function to `ssp-shop-prod-request`.
    2. Set the viewer-response function to `ssp-shop-prod-response`.
    3. Set the real-time log configuration to `ssp-shop-prod`.

    Do this for every cache behavior that serves the site, such as
    `/assets/*`. A behavior without the functions gives the arms the files
    of live.
  </Step>

  <Step title="Check the app">
    ```shell
    ssp app show shop-prod
    ```

    The output shows the live commit and the orchestrator `cloudfront`.
    The log of the service shows a warning for each cache behavior that
    lacks the functions or the real-time log.
  </Step>
</Steps>

## Rules at the edge

`ssp` translates `subject` and `eligibility` into JavaScript. A rule that
it cannot translate is an error: the arms of that experiment are not
ready, and the start fails with the reason. The edge supports:

- `request.method`, `request.path`, and the maps `request.query`,
  `request.headers`, and `request.cookies`;
- `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `||`, `!`, `? :`, `in`, and `+`;
- `contains`, `startsWith`, `endsWith`, `size`, `has`, and `matches` with
  a literal pattern;
- strings, integers, booleans, `null`, and lists.

CloudFront names its viewer headers otherwise than other CDNs. The country
header is `cloudfront-viewer-country`, not `cf-ipcountry`:

```toml statespace.toml
[experiment.us-landing]
eligibility = '''
request.headers["cloudfront-viewer-country"] == "US"
'''
```

A viewer header gets to the functions only when the origin request policy
of the cache behavior adds it. Add each viewer header that the rules use.
`ssp` warns about a header that no policy adds.

<Note>
  Keep the cookies `ssp_sid` and `ssp` out of the cache key. When they are
  in the cache key, each visitor gets their own cache entries. The arms do
  not need them in the key: their paths are different.
</Note>

## Your own viewer-request function

CloudFront runs one viewer-request function for each cache behavior. When
your site has its own function, such as a router, give its name to `ssp`.

```shell
ssp proxy cloudfront --app shop-prod \
  --distribution E2EXAMPLE \
  --bucket shop-prod-site \
  --stream ssp-shop-prod-requests \
  --viewer-request-function shop-router
```

In the template, set the parameter `ViewerRequestFunction`. Then:

1. `ssp` reads the code of your function.
2. It publishes one function that runs the Statespace step first, then
   your handler.
3. For a subject of an arm, it puts `/arms/<commit>` in front of the path
   that your handler returns.
4. A response from your handler, such as a redirect, goes out as it is.
5. When you publish a change to your function, `ssp` publishes the
   combined function again.

Attach `ssp-shop-prod-request` in place of your function. The combined
code must fit the 10 KB of a CloudFront function. `ssp` fails with a
clear error when it does not.

## Records

- `ssp` records the requests of the arms from the real-time log. It does
  not record live.
- The log needs these fields: `timestamp`, `time-to-first-byte`,
  `sc-status`, `sc-bytes`, `cs-method`, `cs-uri-stem`, `cs-bytes`,
  `time-taken`, `cs-uri-query`, and `viewer-request-log-data`. Events that
  use `request.headers` or `request.cookies` also need `cs-headers` or
  `cs-cookie`. The template adds all of them.
- A static site has no output. Events on `stdout` and `stderr` never match.
- CloudFront sends real-time logs on a best-effort basis. A record can come
  late, or, rarely, not at all. Losses hit all arms alike.
- One shard of the stream takes 1,000 records a second. For a busy site,
  set the template parameter `ShardCount`. Kinesis keeps unread records for
  24 hours, so a slow reader delays results but loses nothing.
- Several tasks of the service split the shards of the stream. ECS adds
  tasks when the records wait in the stream.

## Stop and overrides

- `ssp experiment stop` removes the arms from the KeyValueStore in seconds.
  While `ssp proxy cloudfront` is down, the edge keeps the last shares, so
  a stop waits for the service. As a last resort, detach the functions
  from the distribution.
- The functions verify [signed override links](/concepts/overrides) with
  the override key of the app, from the KeyValueStore.
- CloudFront does not run the viewer-response function for an error
  status of 400 or more. Such a response sets no cookie.

## Permissions

The template gives the role of the service only these permissions:

1. Describe, read, update, and publish the two functions.
2. Read and write the one KeyValueStore.
3. Read the configuration of the distribution, its real-time log, and its
   cache and origin request policies.
4. Read the one Kinesis stream.
5. List the bucket, read its files, and write and delete under `arms/`.
6. Pull the images of the builds from the ECR repository that you name.

`ssp` uses the AWS default credential chain. On ECS, this is the task role.
For a registry other than ECR, `ssp` reads the credentials of the Docker
configuration, or pulls a public image.
