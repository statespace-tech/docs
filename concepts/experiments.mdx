What is an experiment, and when do its results start again?

## Experiments

An experiment is a named comparison of commits in one app. Its table in `statespace.toml` defines who can enter and how much traffic it can get. The CLI sets its arms.

```toml statespace.toml
[experiment.checkout]
subject = 'request.headers["x-user-id"]'
max_traffic = 0.2
```

- The experiment exists in an app when the `statespace.toml` of the app's live commit has its table. It begins `stopped`, with no arms.
- Each app of the folder has its own arms and state for the experiment. `checkout` can run on `shop-dev` and be stopped on `shop-prod`.
- An experiment can have its own events. See [Shared and own](/concepts/events#shared-and-own).
- When a release removes the table, the experiment is `gone`. Statespace keeps its history and results. `ssp experiment list --all` shows it.

## Arms

An arm is one commit in one experiment, with an exact share of the app's subjects. The commit is the arm's ID.

```shell
ssp experiment update checkout \
  --arm c0ffee1=0.05 --arm a1b2c3d=0.05
```

- The share is a fraction, such as `0.05`. It is never `5` or `5%`.
- The shares of the arms add up to `max_traffic` or less.
- Any commit with a build for the app can be an arm. This includes the live commit and older commits.
- Each arm is a fixed commit. An arm never follows a branch or live.
- One commit in two experiments runs as two copies, one for each experiment.

## Change the arms

`ssp experiment update` changes only the arms that you name. For example, `checkout` has the arms `c0ffee1=0.05` and `a1b2c3d=0.05`:

| You run | Result |
| --- | --- |
| `--arm e5f6a7b=0.04` | `e5f6a7b` is added with `0.04`. The two other arms stay |
| `--arm c0ffee1=0.06` | `c0ffee1` gets `0.06`. `a1b2c3d` stays |
| `--arm a1b2c3d=0` | `a1b2c3d` is removed. Its results stay |
| `--arm a1b2c3d=0 --arm f6a7b8c=0.05` | `f6a7b8c` replaces `a1b2c3d` |

An arm that you do not name never changes. So when you forget an arm, Statespace does not remove it.

You cannot change the arms of a running experiment. Stop it, update it, and start it again.

## No arm is special

The results show the arms in the order that you added them. Each arm has its own numbers, and the commit status of each arm says `running`.

To compare a change with live, add the live commit as an arm.

## Start and stop

An experiment has these states:

| State | Means |
| --- | --- |
| `stopped` | No arm gets traffic. You can change the arms |
| `starting` | The proxy starts one copy of each arm. No arm gets traffic yet |
| `running` | Each arm gets its share |
| `gone` | The table is not in the live `statespace.toml` |

`ssp experiment start` makes these checks, in this order:

1. The experiment has 2 or more arms.
2. The shares add up to `max_traffic` or less.
3. Each arm has a build for the app.
4. The shares of all running experiments of the app, and of this one, add up to 1 or less.

When a check fails, nothing changes, and the command says why. Then the experiment is `starting`, and the command waits. When each arm is ready, the experiment is `running`. When an arm is not ready in 5 minutes, the proxy stops the copies, and the experiment is `stopped` again. The command gives the reason for each arm.

`ssp experiment stop` takes the arms out of traffic in seconds. There is no stop for one arm and no stop for a whole app. See [Stop in an emergency](/guides/emergency-stop).

Each start and stop records who did it, how (`cli`, `dashboard`, or `api`), the note, and the time.

## Versions

A version is one run of an experiment, from `start` to `stop`. Each start begins a new version, such as `checkout` v3. A version keeps the same arms, shares, and definition from start to stop. So the results of one version never mix two setups. When a version stops, Statespace keeps its results. See [Versions](/concepts/evidence#versions).

An arm that stays in the experiment from one version to the next keeps its ranges of the hash space. So its subjects see the same arm in the next version.

## What a release does

A release changes the live commit, and with it `statespace.toml`. Each running experiment then gets one of these results.

| The release changes | Result |
| --- | --- |
| Only code | Nothing. The arms are fixed commits. The dashboard says "live is now f2f2f2f" |
| `subject`, `eligibility`, or `max_traffic` of the experiment, or removes its table | The experiment stops |
| A shared event | Every running experiment of the app stops |
| An own event of the experiment | The experiment stops |

When a release stops an experiment, the note of the stop is "definition changed in live d00d123". `ssp experiment list`, the commit statuses, and the audit log give the reason and the start command to run again.

When the live commit contains an arm's commit, nothing changes. The dashboard says "live c0ffee1 contains a1b2c3d". You decide when to stop the experiment.
