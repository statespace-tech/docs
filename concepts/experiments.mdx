This page answers: what is an experiment, how do you stop it, and when do its results start again?

## Experiments

An experiment is a named comparison of commits in one app. Its table in `statespace.toml` sets who can enter and how much traffic it can get. The CLI sets its arms.

```toml statespace.toml
[experiment.checkout]
subject = 'request.headers["x-user-id"]'
max_traffic = 0.2
```

- The experiment exists in an app when the `statespace.toml` of the live commit has its table. It begins `stopped`, with no arms.
- Each app has its own arms and state for the experiment. `checkout` can run on `shop-dev` and be stopped on `shop-prod`.
- When a release removes the table, the experiment is `gone`. Statespace keeps its history and results.

## Arms

An arm is one commit in one experiment, with an exact share of the app's subjects. The commit is the arm's ID.

```shell
ssp experiment update checkout \
  --arm c0ffee1=0.05 --arm a1b2c3d=0.05
```

- A share is a fraction, such as `0.05`. The shares add up to `max_traffic` or less.
- Any commit with a build for the app can be an arm, also the live commit and older commits.
- An arm is a fixed commit. It never follows a branch or live.
- No arm is special. To compare a change with live, add the live commit as an arm.
- `update` changes only the arms that you name. `=0` removes an arm. Its results stay.
- You cannot change the arms of a running experiment. Stop it, update it, and start it again.

## Start

| State | Means |
| --- | --- |
| `stopped` | No arm gets traffic. You can change the arms |
| `starting` | The proxy starts one unit for each arm. No arm gets traffic yet |
| `running` | Each arm gets its share |
| `gone` | The table is not in the live `statespace.toml` |

`ssp experiment start` makes these checks, in this order:

1. The experiment has 2 or more arms.
2. The shares add up to `max_traffic` or less.
3. Each arm has a build for the app.
4. The shares of all running experiments of the app, with this one, add up to 1 or less.

When a check fails, nothing changes. When an arm is not ready in 5 minutes, the units stop, and the experiment is `stopped` again. The command gives the reason for each arm.

## Stop

`ssp experiment stop` takes one or more names. The arms leave traffic in seconds, and their subjects go to live. The units stop. Statespace keeps the results.

```shell
ssp experiment stop checkout --app shop-prod \
  --note "checkout errors > 2%"
```

- Stop never asks for confirmation. A stop on a stopped experiment changes nothing.
- There is no stop for one arm, and no stop for a whole app.

To stop all experiments of an app, list the running ones, and give all the names to `stop`:

```shell
ssp experiment list --app shop-prod --running
ssp experiment stop checkout us-landing \
  --app shop-prod --note "incident 214"
```

You can also stop an experiment in the dashboard. Each start and stop records who did it, how, the note, and the time.

## Versions

A version is one run of an experiment, from start to stop. Each start begins a new version, such as `checkout` v3. A version keeps the same arms, shares, and definition from start to stop. So the results of one version never mix two setups.

An arm that stays from one version to the next keeps its ranges of the hash space. So its subjects see the same arm again.

## What a release does

A release changes the live commit, and with it `statespace.toml`.

| The release changes | Result |
| --- | --- |
| Only code | Nothing. The arms are fixed commits |
| `subject`, `eligibility`, or `max_traffic` of the experiment, or removes its table | The experiment stops |
| A shared event | Every running experiment of the app stops |
| An own event of the experiment | The experiment stops |

The note of such a stop is, for example, "definition changed in live d00d123". When the live commit contains an arm's commit, nothing changes. You decide when to stop.
