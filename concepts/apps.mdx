This page answers: what is an app, and how does Statespace know which commit runs live?

## Apps

An app is one running copy of a service, with one proxy in front of it. A development copy and a production copy of one service are two apps, such as `shop-dev` and `shop-prod`.

```shell
ssp app add shop-prod --note "shop, production"
```

- An app is linked to one repo and one folder: the folder of `statespace.toml`. Its builds come from that repo.
- Several apps can come from one folder. Each experiment of the folder exists in each app, with its own arms and state.
- An app can have its own settings in an `[app.<name>]` section of `statespace.toml`.
- Each app is an independent layer. See [Apps are layers](/concepts/subjects-and-eligibility#apps-are-layers).
- Only `ssp app add` makes an app. The proxy gets its app from its runtime token.
- `ssp app remove` deletes the app and all its data.

See [ssp app](/reference/cli/app) for the name rules and flags.

## Builds

A build is the record of what one commit runs. It is one of these:

- **An image**, by digest, such as `ghcr.io/acme/shop@sha256:…`. Docker, Kubernetes, AWS Fargate, Google Cloud Run, Fly.io, and AWS Lambda run images.
- **A folder of files** in a bucket, such as `s3://acme-site/builds/a1b2c3d…/`. Amazon S3 and Google Cloud Storage serve files.

Your CI records each build with `statespace-tech/action@v1`. GitHub's OIDC token proves the repo and the commit, so CI keeps no Statespace secret. See [GitHub Actions](/guides/github-actions).

- Statespace records builds of every branch. A branch name means nothing to Statespace.
- A build can be for one app only, such as when it holds values for that app.
- Statespace never changes or deletes a build. Your registry and your bucket keep them.
- The proxy runs only recorded builds. So a stolen runtime token cannot put new code in front of your users.

## Live

Live is the service that you run and deploy as usual. Statespace does not deploy it.

The proxy reports what live runs: an image, or a hash of the files at the bucket root. Statespace finds the build of that image or those files. The commit of that build is the **live commit**. `ssp app show` prints it.

The `statespace.toml` in the build of the live commit holds the settings and experiments of the app. So a change to the file takes effect when its commit runs as live. See [What a release does](/concepts/experiments#what-a-release-does).

<Warning>
  When live runs an image or files without a build, the app has no live commit, and no experiment can start. Add `statespace-tech/action` to the deploy workflow.
</Warning>
