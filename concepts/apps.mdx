What is an app, and how does Statespace know which commit runs live?

## Apps

An app is one running copy of a service. One proxy is in front of it. A development copy and a production copy of one service are two apps, such as `shop-dev` and `shop-prod`.

```shell
ssp app add shop-prod --note "shop, production"
```

- An app is linked to one repo and one folder: the folder of `statespace.toml`. Its builds come from that repo.
- Several apps can come from one folder. Each app can have its own section in `statespace.toml`, such as `[app.shop-dev]`.
- Only `ssp app add` makes an app. `ssp proxy --app shop-prod` fails when the app does not exist.
- A name has 1 to 63 characters: lowercase letters, digits, and `-`. It is unique in the workspace.

## Builds

A build is a record "commit → image digest". Your CI makes it with `statespace-tech/action@v1` after it builds the image. GitHub's OIDC token proves the repo and the commit, so CI keeps no Statespace secret.

- Statespace records builds of every branch. A branch name means nothing to Statespace.
- Statespace never changes a build.
- The proxy runs only images of recorded builds. A stolen runtime token cannot put new code in front of your users.
- A build can be for one app. Use this when your build puts different values in the image for each app. See [Build labels](/guides/github-actions#build-labels).

## Live

Live is the service that you run and deploy as usual. Statespace does not deploy it.

The proxy reports the image that live runs. Statespace finds the build of that image. The commit of that build is the **live commit**. For example, live runs `ghcr.io/acme/shop@sha256:2222…`, and its build is commit `9f1ce8a`.

The `statespace.toml` in the build of the live commit holds the settings of the app. So a change of a setting takes effect when its commit runs as live.

<Warning>
  When live runs an image without a build, the app has no live commit, and its arms wait. `ssp app show` says "Live runs an image without a build. Add statespace-tech/action to the deploy workflow".
</Warning>

## The control

The control is a copy of the live image. It serves only the control's subjects. Each app has one control for all its arms.

- The proxy starts the control with the first arm.
- When the live image changes, the proxy replaces the control. Each arm starts a new version.
- The proxy stops the control with the last arm.
- The control gets as many subjects as the arm with the largest share.

The control runs the same code as live. But Statespace records only the control. So each request and each output line belongs to one side.
