What runs when you start an experiment, and who decides what?

## The parts

| Part | Where it runs | What it does |
| --- | --- | --- |
| Your CI | GitHub Actions | Builds images or files, and records each build with `statespace-tech/action@v1` |
| `statespace.toml` | Your repo | Holds the events and experiments |
| `ssp proxy` | In front of your app | Assigns each request, runs and labels the arms, and counts their visitors |
| Statespace | `api.statespace.com` | Keeps apps, builds, experiments, and results. Posts commit statuses |
| `ssp` CLI | Your terminal or agent | Adds apps and tokens. Sets arms, and starts and stops experiments |

Your app does not know Statespace. It runs no proxy and needs no code change.

## Alongside live

`ssp` runs alongside live, never inside it.

- You run live as you do now, with your own deploys and your infrastructure as code. Live keeps its own address.
- `ssp` runs next to live, in front of it. It never changes a resource that it did not create.
- Each arm is a resource that `ssp` creates, labels, and deletes, such as a container, a Deployment, or a Cloud Run service.

This gives you three things:

1. The tools that manage live keep working with no setting, such as Terraform, Helm, Argo CD, or Compose. See [Infrastructure as code](/guides/infrastructure-as-code).
2. When `ssp` is down, the load balancer or CDN in front of it can send traffic to the address of live. See [Fall back to live](/guides/fall-back-to-live).
3. When you remove `ssp`, your setup stays as it is.

## A request

<TrafficDiagram />

In this example, the app `shop-prod` runs two experiments. `checkout` has two arms of 5% each. `us-landing` has one arm of 5% that you can see. For each request, the proxy does these steps:

1. It takes the running experiments in the order of `statespace.toml`.
2. For each experiment, it reads the subject ID and checks `eligibility`.
3. It hashes the subject ID to a point between 0 and 1.
4. When the point is in the range of an arm of the experiment, the request goes to that arm.
5. When no experiment takes the request, it goes to live.

The proxy never waits on Statespace during a request. It gets its configuration in the background. When something is wrong, the request goes to live. See [Subjects and assignment](/concepts/subjects).

## Live and the arms

- **Live** is the service that you run now. It serves every request outside the experiments. Statespace never counts it.
- **An arm** is one commit in one experiment. The proxy runs a copy of the commit's image for it, or serves the commit's files. The proxy counts its visitors.
- **A unit** is the running copy of one arm. The proxy runs units on the platform of live: Docker, Kubernetes, Cloud Run, ECS Fargate, or Fly.io. On S3 and Cloud Storage, a unit is the build folder of the arm, and the proxy serves its files.

There is no special control arm. To compare a change with what runs now, add the live commit as an arm. Then both arms get the same kind of subjects at the same time, and the proxy counts both the same way.

## Who decides

- Your CI decides which builds exist. The proxy runs only recorded builds.
- A person or an agent with permission on the repo sets the arms and starts each experiment. Statespace never starts an experiment by itself.
- `statespace.toml` in your repo defines the settings and the experiments. They change only with a commit.
- Statespace shows numbers for each arm. You and your agents decide what they mean.
