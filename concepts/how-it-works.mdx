This page answers: what runs when you start an experiment, and who can change it?

## The parts

| Part | Where it runs | What it does |
| --- | --- | --- |
| Your CI | GitHub Actions | Makes builds, and records each one with `statespace-tech/action@v1` |
| `statespace.toml` | Your repo | Holds the events and experiments |
| `ssp proxy` | In front of your app | Assigns each request, runs the arms, and counts their subjects |
| Statespace | `api.statespace.com` | Keeps apps, builds, experiments, and results. Posts commit statuses |
| `ssp` CLI | Your terminal or agent | Adds apps and tokens. Sets arms, and starts and stops experiments |

Your app needs no code change.

## Alongside live

**Live** is the service that you run and deploy now. The proxy runs next to live, in front of it. It never changes a resource that it did not create. Each arm is a resource that the proxy creates, labels, and deletes, such as a container.

So the tools that manage live keep working, such as Terraform or Helm. See [Infrastructure as code](/guides/infrastructure-as-code). When the proxy is down, a CDN can send traffic to live. See [Put a CDN in front](/guides/cdn).

## A request

<TrafficDiagram />

In this example, `shop-prod` runs two experiments. The proxy hashes the subject of each request to an arm of an experiment, or to live. See [Subjects and assignment](/concepts/subjects-and-eligibility).

The proxy never waits on Statespace during a request. It gets its configuration in the background.

An **arm** is one commit in one experiment. A **unit** is the running copy of one arm. There is no control arm: to compare a change with live, add the live commit as an arm. Statespace never counts live.

## Who decides

- Your CI decides which builds exist. `statespace.toml` defines the events and experiments, and changes only with a commit.
- A person or an agent starts each experiment. Statespace never starts one by itself.
- Statespace shows numbers for each arm. You and your agents decide what they mean.

## Permissions

Each app is linked to a repo. Your role on that repo on GitHub decides what you can do. There are no Statespace roles. The CLI and the dashboard use the same rule.

| Level | Allows | GitHub role |
| --- | --- | --- |
| `read` | See apps, experiments, and results | Read, Triage |
| `write` | Update, start, and stop experiments | Write, Maintain |
| `admin` | Add and remove apps and runtime tokens. Erase subjects | Admin |

Statespace keeps roles for 10 minutes. So stop works while GitHub is down.

### Credentials

The CLI uses the first credential that it finds, in this order:

1. `STATESPACE_TOKEN`.
2. The session from `ssp login`.
3. A GitHub user token in `GH_TOKEN` or `GITHUB_TOKEN`: `gho_`, `ghp_`, `ghu_`, or `github_pat_`. Statespace asks GitHub who it is.
4. In GitHub Actions, the OIDC token of the job. A workflow of the app's repo counts as `write`.

`ssp whoami` shows which credential the CLI uses.

### Runtime tokens

A runtime token is the only kind of Statespace token. It is for one app, and the proxy uses it. An app can have several tokens, so you can rotate them.

A runtime token can read the name and runtime configuration of its app, hold the lease, and send counts. It cannot change experiments or read results. The CLI shows its secret one time only: keep it in a secret manager.
