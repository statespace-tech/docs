title: Overrides
description: How a tester opens an arm of a running experiment with a URL parameter or a header.
---

How do you look at an arm yourself, without the random split?

An override is a request that names its experiment and arm. The app must allow overrides in `statespace.toml`. The default is `false`.

```toml statespace.toml
[app.shop-dev]
overrides = true
```

## Open an arm

| Client | Send | The proxy |
| --- | --- | --- |
| Browser | `https://shop-dev.acme.com/?ssp_arm=checkout:a1b2c3d` | Sets the cookie `ssp_arm`, and redirects a `GET` to the same URL without the parameter |
| API | The header `ssp-arm: checkout:a1b2c3d` on each request | Uses the arm for that request |

- The value is `<experiment>:<commit>`. The commit is the full commit, or its first 7 characters or more. The value must match one arm of a running experiment of the app.
- The cookie lasts 1 hour. Each request renews it.
- An empty `?ssp_arm=` ends the override.
- Another value gets a short page, such as "checkout:a1b2c3d is not running on shop-dev. Running: checkout:c0ffee1, checkout:f6a7b8c, us-landing:b2c3d4e".
- You cannot pick live.
- Your app never sees `ssp_arm` or `ssp-arm`.

`ssp experiment show` and the dashboard show the override link of each arm when the app allows overrides.

## Records

Statespace records override visits with the reason `override`. They count fully for the experiment: subjects, events, and metrics. So you can assign arms with your own `ssp_arm` links. Only the split check leaves them out.

<Warning>
  Anyone who can reach the proxy can open an arm with an override. Turn on overrides only for apps that are not public, such as `shop-dev`.
</Warning>
