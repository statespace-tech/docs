---
title: Random assignment
description: Keep subject assignments consistent across SDKs.
---

Random assignment gives each eligible subject one group. Each published experiment version records its definition and allocation ranges.

## Stable identity

Choose an identifier at the level where treatment can vary independently. Label user-level assignment when creating the experiment.

```shell
ssp experiment create --name rank-v2 --assignment user_id --variant atlas-search@1=0.2
```

The label does not read a context field. Supply the identifier value explicitly to the SDK.

```python
rank = run.get_function("u_42", default=lambda items: items)
result = rank([3, 1, 2])
```

## Stable bucket

All SDKs calculate the same bucket from the experiment salt and subject ID.

```text
bucket = first 53 bits of SHA-256(assignment_salt + ":" + subject_id) / 2^53
```

The same subject, salt, and allocation ranges produce the same group across Python, TypeScript, Go, and service instances. The SDK keeps the subject's assignment within its session.

## Group allocation

Published candidate functions have explicit bucket ranges. The remaining interval belongs to control. For a new experiment with one 20% candidate, the allocation is shown below.

```text
atlas-search@1: [0.0, 0.2)
control:       [0.2, 1.0)
```

## New versions

Function-experiment updates preserve the active version's salt. If no version is running, the update uses the latest version's salt. The backend retains existing candidate ranges where their new weights permit it. New or expanded candidates use available ranges.

Changes to weights or function versions can still move subjects between groups. Analyze each experiment version separately. Starting a draft stops new assignments to the previous running version.

## Forced assignment

Forced assignment is not exposed by the current function CLI. Keep manual overrides out of a randomized comparison. A separate diagnostic path does not provide the same inference as random assignment.
