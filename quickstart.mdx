In this tutorial, you test a change to the app `shop-dev` on live traffic. The app runs on one machine with Docker. At the end, the experiment `checkout` runs: 5% of the subjects get the live commit, and 5% get your change. The commit status `statespace/shop-dev/checkout` on each commit shows the evidence.

## Prerequisites

- A GitHub repo with a `Dockerfile`, such as `acme/shop`. The `Dockerfile` names one port with `EXPOSE`, such as `EXPOSE 3000`.
- A Linux machine with Docker and Docker Compose. You run the app on this machine with Compose.
- The admin role on the repo. You need it to add the app and its token.

## Run your first experiment

<Steps>
  <Step title="Install the GitHub App">
    On [statespace.com](https://statespace.com), select **Connect GitHub**. Install the Statespace GitHub App on the account that owns the repo. The App can read code, metadata, and members, and write commit statuses. It cannot write code.
  </Step>

  <Step title="Write statespace.toml">
    In the root folder of the repo, write this starter file. It has one event and one experiment. A coding agent can write this file for you.

    <StarterToml />

    Change the event to a route of your app. See [statespace.toml](/reference/statespace-toml) for every key.
  </Step>

  <Step title="Build every push">
    Add the workflow below to the repo. It builds each push to each branch, pushes the image to GitHub Packages, and records the build. A static site records a folder of files instead. See [GitHub Actions](/guides/github-actions).

    <BuildWorkflow />

    Commit both files, and push them to `main`.

    ```shell
    git add statespace.toml .github/workflows/build.yml
    git commit -m "Record builds with Statespace"
    git push
    ```

    When the workflow is done, the build of this commit is recorded.
  </Step>

  <Step title="Install the CLI">
    Install the CLI, and sign in with the same GitHub account.

    ```shell
    curl -fsSL https://statespace.com/install.sh | bash
    ssp login
    ```
  </Step>

  <Step title="Add the app">
    In the repo folder, add the app. The CLI reads the repo from the `origin` remote, and the folder from the nearest `statespace.toml`. It prints what it found.

    ```shell
    ssp app add shop-dev --note "shop on the dev machine"
    ```
  </Step>

  <Step title="Add a runtime token">
    Add a token for the proxy. The CLI shows the secret only one time.

    ```shell
    ssp token add --app shop-dev --note "Docker proxy"
    ```

    On the machine, put the secret in `.env`, next to `compose.yaml`.

    ```shell .env
    STATESPACE_TOKEN=<secret>
    ```
  </Step>

  <Step title="Run the proxy">

    On the machine, write `compose.yaml`. The service `shop` runs live: the build of `main`, by digest. The service `ssp` runs the proxy next to it, on port 80. When your app runs with Compose already, add `container_name: shop` and the service `ssp` to your file.

    ```yaml compose.yaml
    services:
      shop:
        image: ghcr.io/acme/shop@sha256:<digest>
        container_name: shop
        restart: unless-stopped

      ssp:
        image: ghcr.io/statespace-tech/statespace:0.5.0
        command:
          - proxy
          - docker
          - --live-container
          - shop
        environment:
          STATESPACE_TOKEN: ${STATESPACE_TOKEN}
        ports:
          - "80:8080"
        volumes:
          - /var/run/docker.sock:/var/run/docker.sock
        user: root
        restart: unless-stopped
        stop_grace_period: 30s
    ```

    Start the project. Point your traffic at port 80.

    ```shell
    docker compose up -d
    ```

    The proxy sends live traffic to the container `shop`. It runs each arm as a copy of that container. The socket gives `ssp` control of Docker on the machine. See [Docker](/guides/docker#the-docker-socket).

    The commit of `main` is now the live commit. Its `statespace.toml` defines the experiment `checkout`.
  </Step>

  <Step title="Push a change">
    Make a change on a new branch, and push it. CI builds the commit and records it.

    ```shell
    git switch -c one-page-checkout
    git commit -am "Put checkout on one page"
    git push -u origin one-page-checkout
    ```
  </Step>

  <Step title="Set the arms">
    When the workflow is done, set the arms of `checkout`. The live commit is the first arm. Your change is the second arm. Each arm gets 5% of the subjects.

    ```shell
    ssp app show shop-dev
    ssp experiment update checkout --app shop-dev \
      --arm c0ffee1=0.05 \
      --arm "$(git rev-parse HEAD)=0.05"
    ```

    Use the live commit that `ssp app show` prints in place of `c0ffee1`. The command prints the arms and the total of the shares.
  </Step>

  <Step title="Start the experiment">
    Start the experiment. The proxy starts one copy of each arm. The command waits until each arm is ready, for 5 minutes at most.

    ```shell
    ssp experiment start checkout --app shop-dev \
      --note "one-page checkout"
    ```

    When both arms are ready, the experiment is `running`, and the proxy sends each arm its share.
  </Step>

  <Step title="Read the evidence">
    <Planned />

    Show the experiment. It prints the results of each arm: the p50, p95, and p99 latency, and for each event the share of subjects with one or more matches, with a 95% interval. The events `requests_4xx` and `requests_5xx` come first.

    ```shell
    ssp experiment show checkout --app shop-dev
    ```

    Each arm's commit on GitHub has the status `statespace/shop-dev/checkout`. While the experiment runs, the status of your change says, for example:

    ```text
    v1 running · 0.05 · purchase 0.0261 [0.0184, 0.0368]
    · 1,188 subjects · split OK
    ```

    Statespace updates the status at each change of state, and every hour. Select **Details** to see the experiment in the dashboard.
  </Step>

  <Step title="Stop the experiment">
    When you have the evidence that you need, stop the experiment. The arms leave traffic in seconds. Statespace keeps the results.

    ```shell
    ssp experiment stop checkout --app shop-dev \
      --note "enough data"
    ```

    To ship the change, merge the branch and deploy it as usual.
  </Step>
</Steps>
