---
title: Quickstart
description: Build a function, run an experiment, and inspect its evidence.
---

This example tests a sorted search result against the application's default.
The published function is named `atlas-search`. The experiment is `rank-v2`.
Use the current CLI and SDK checkouts with a running backend. GitHub or Google
login requires registered provider clients on that backend.

<Steps>
  <Step title="Build the CLI and sign in">
    Install the CLI from its checkout in the parent workspace.

    ```shell
    cargo install --path cli --locked
    export STATESPACE_URL=http://localhost:8080
    ssp login
    ```

    Sign in with a configured provider, then approve the displayed device code.
    Use the service's HTTPS URL for a hosted installation.
  </Step>

  <Step title="Define the function">
    Save the candidate computation as `rerank.py`.

    ```python
    def rerank(items: list[int]) -> list[int]:
        return sorted(items)
    ```

    The function receives and returns JSON-compatible values. It executes in
    the application's local Wasm runtime.
  </Step>

  <Step title="Build and publish the function">
    Build the Python computation component and publish version 1.

    ```shell
    ssp function build ./rerank.py --language python --entry rerank:rerank --output rerank.wasm
    ssp function publish rerank.wasm --name atlas-search
    ```

    The build requires the Python component toolchain. The CLI reports missing
    tools. S3 stores the artifact; PostgreSQL stores its hash and provenance.
  </Step>

  <Step title="Create and start the experiment">
    Assign half the traffic to the published function and start the draft.

    ```shell
    ssp experiment create --name rank-v2 --variant atlas-search@1=0.5
    ssp experiment start --name rank-v2 --version 1
    ```

    The remaining half uses the application's control default. Later updates
    create immutable versions. Starting one stops the previous running version.
  </Step>

  <Step title="Create a deployed SDK key">
    Create a runtime key and store its secret as `SSP_API_KEY` in the application.

    ```shell
    ssp key create --name production --preset runtime
    ```

    Local SDKs can use the saved CLI login. Keep creation responses out of logs.
    Configure `STATESPACE_URL` in the application to use the same service.
  </Step>

  <Step title="Run and log an outcome">
    Install the Python SDK from its adjacent checkout.

    ```shell
    pip install -e ./python-sdk
    ```

    Assign a subject, execute its function, and log JSON evidence.

    ```python
    import statespace

    with statespace.init("rank-v2") as run:
        rank = run.get_function("u_42", default=lambda items: items)
        result = rank([3, 1, 2])
        run.log("u_42", {"relevance": 0.7, "result": result})
    ```

    Closing the session flushes delivery and reports errors. Each event must
    fit within 64 KiB. The default retention is 90 days with a 10 GiB account
    event quota. SQS and the worker persist accepted events asynchronously.
  </Step>

  <Step title="Inspect the evidence">
    Create a read-only account database credential for an analysis tool.

    ```shell
    ssp database credential create --name analyst
    ```

    Store the returned connection settings securely. Hosted Lightsail access
    uses an SSH tunnel. Supply the connection through protected PostgreSQL
    environment settings, then inspect the logs view.

    ```shell
    psql -c "SELECT experiment_version, group_name, data FROM statespace.logs WHERE experiment_name = 'rank-v2'"
    ```

    The CLI has no SQL query command. The account credential can read only its
    own event tables and logs view.
  </Step>
</Steps>
