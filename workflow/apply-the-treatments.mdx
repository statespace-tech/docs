Open a pull request when the outcome is in production and the branch is pushed. Write the hypothesis in its description.

```shell
gh pr create --title "Rank results by recent clicks" \
  --body "Sorted results get more clicks."
```

## What runs

GitHub decides whether the arm may run. The arm runs while its pull request can merge.

<WhatRuns />

## The Statespace check

The `Statespace` check on each commit of the branch tells what runs, and why the arm waits. Its title also gives the experiment's share of the app's subjects, such as `Running at 10% (+10% control), 20% in the experiment`.

The check fails only when CI could not record the commit, such as for an invalid `statespace.toml`. A wait never fails it, so a wait never blocks a merge.

While a version runs, the check shows the evidence of each arm and control. It is not a verdict. Compare the arms in SQL before you decide.

| Row | Shows |
| --- | --- |
| Share | The share of the app's subjects |
| Subjects | The subjects that the proxies assigned to it |
| Requests | The requests that it served |
| Errors (5xx) | The share of its requests with a 5xx status |
| p90 latency | The 90th percentile of its request duration |
| Events | The five `event` values that the arms printed most |

From 100 subjects, the check also tests whether the subjects split as the shares say. A mismatch, at p < 0.001, means that you cannot trust the comparison until you find the cause. Statespace updates the check about every 5 minutes.

## Fair comparisons

Statespace also makes sure that the comparison is fair:

- The arm's base must have run as the default. Until a proxy runs it, the arm waits.
- Each base has its own control, which runs the default build of that base.
- The arms fit in the app's traffic limit, first come, first served.

## Run the proxy

Run the app behind `ssp proxy`, with a runtime token as `SSP_TOKEN`. A token for one app, from `--preset runtime --app atlas`, gives the proxy its app.

```shell
ssp proxy --health /health \
  --image ghcr.io/acme/atlas:main
```

The proxy runs the default image as a container, and a container for each arm and control. A container gets traffic when `--health` answers 200. The proxy reports the digest of its default, so Statespace knows the deployed commit.

On Kubernetes, the proxy runs beside the default in each pod, and `ssp controller kubernetes` runs the arms. See [Deployment](/getting-started/deployment).

## Keep arms apart from shared state

Give arms their own environment with `--arm-env`. Controls get it too, so both sides of the comparison run the same way.

```shell
ssp proxy --image ghcr.io/acme/atlas:main \
  --arm-env DATABASE_URL="$ARM_DATABASE_URL" \
  --arm-env SCHEDULER_ENABLED=false \
  --arm-env CACHE_PREFIX=arm
```

<Warning>
  Arms use the same database, cache, and queues as the default. Give arms a database user without schema permissions. Put migrations in the deployed code first. Turn off schedulers in arms, so nothing runs twice.
</Warning>

## Record what arms print

Arms record each line that they print on standard output and standard error. The proxy also writes each line to its own output, so your log collection keeps working. `--redact` replaces matches before lines leave the machine.

```shell
ssp proxy ... --redact 'sk_live_\w+'
```

JSON lines keep their fields. A `subject` field ties a line to that subject's arm. Arms also record each request, lifecycle events, CPU and memory, and HTTP summaries for each minute. Statespace never records the default.

## Check the arms

Make sure that the arms run before you wait for outcomes.

```shell
ssp status https://github.com/acme/atlas/pull/418
```

Without a target, `ssp status` shows the arm of the `exp/` branch that you are on. Outside an `exp/` branch, it shows the app or repository that you are in. Below the table, it gives each experiment's share of the app's subjects, such as `recent-clicks holds 20% of atlas's subjects.` For the proxies and the arm events, query the app's views.

```sql
SELECT id, kind, version, report FROM atlas.hosts;
SELECT timestamp, arm, commit, event, data
FROM atlas.lifecycle ORDER BY timestamp DESC LIMIT 20;
```

## Change the arm

Push a new commit. When it can merge, it replaces the running commit. The arm keeps its subjects, and the experiment gets a new version. The evidence keeps its version and commit.

To change the share or the rules, change `statespace.toml` on the branch, and push. To change only the share, use **Edit** on the arm in the dashboard. The Statespace App commits the change to the branch, with you as co-author. **Edit** needs the write role on the repository.

## Stop and resume

A stop takes arms off traffic at once. Their subjects get the default within seconds. The pull requests do not change, and GitHub is not necessary.

```shell
ssp stop atlas
ssp stop atlas/ranking
ssp stop exp/ranking/recent-clicks --reason "errors > 2%"
```

| Target | Stops |
| --- | --- |
| An app, such as `atlas` | Every experiment of the app, also experiments that start later |
| An experiment, such as `atlas/ranking` | Every arm of the experiment, also arms that open later |
| A branch, such as `exp/ranking/recent-clicks` | That arm |
| A pull request URL | Its arm, in each app that it runs in |
| A repository URL | Every app of the repository |
| A path, such as `.` | The app of the nearest `statespace.toml` |

**Stop** in the dashboard does the same for an app, an experiment, or an arm.

A stop is a hold that Statespace keeps. While a hold covers an arm:

1. The arm does not run, also after a new push.
2. Its `Statespace` check fails, for example `Stopped by octocat with ssp stop · errors > 2%`. If your repository requires the check, the pull request cannot merge.
3. `ssp status` and the dashboard show who stopped it, when, and why.

To run it again, resume the same target:

```shell
ssp resume exp/ranking/recent-clicks
```

A resume clears only the hold on its target. Other holds stay. For example:

1. At 02:00, an alert stops the app: `ssp stop atlas`.
2. At 02:10, a person stops one arm: `ssp stop exp/ranking/recent-clicks`.
3. At 03:00, `ssp resume atlas` runs the other experiments again. `recent-clicks` stays stopped until `ssp resume exp/ranking/recent-clicks`.

A resume does not start an arm that GitHub does not allow. The arm runs again only while its pull request can merge.

A stop and a resume need the triage role on the repository, or a token with the `experiments:write` scope. An alert can stop an app through the API:

```shell
curl -X POST https://api.statespace.com/v1/stop \
  -H "authorization: Bearer $STATESPACE_TOKEN" \
  -d '{"targets": [{"app": "atlas"}],
       "reason": "checkout errors > 2%"}'
```

## Look at an arm

To see a running arm yourself, use a proxy with [`--overrides`](/reference/proxy#overrides). Add the branch to any URL of the app:

```text
https://staging.atlas.dev/?ssp_arm=exp/ranking/recent-clicks
```

The proxy sends you to the same URL without the parameter, and keeps you on the arm for one hour of activity. To leave the arm, open a URL with an empty `?ssp_arm=`.

For an API, send the header on each request:

```shell
curl https://api.atlas.dev/search?q=maps \
  -H 'ssp-arm: exp/ranking/recent-clicks'
```

The `Statespace` check of each pull request shows both forms. Only arms that run can be opened. Your visits are recorded with the reason `override`. They do not count as subjects of the arm, but the lines the arm prints count in its events.

## Ship the arm

To ship an arm, merge its pull request, and deploy as usual.

<Note>
  A merge ends the experiment. Its other arms run again after you update them with the default branch.
</Note>

## Troubleshooting

The `Statespace` check and `ssp status` show why an arm waits. Find the reason below.

<AccordionGroup>
  <Accordion title="The pull request cannot merge">
    The arm runs only while GitHub says that the pull request can merge.

    | Reason | Do this |
    | --- | --- |
    | it needs approval | Get the approval that branch protection requires |
    | a required check or rule blocks the merge | Fix the failed check, or meet the rule |
    | it is behind the default branch; update it | Update the branch with the default branch |
    | it has conflicts with the default branch | Resolve the conflicts, and push |
    | GitHub is checking whether it can merge | Wait until GitHub finishes the check |

    While it waits, the arm runs the last commit that could merge, if there is one.
  </Accordion>

  <Accordion title="The pull request is stopped">
    | Reason | Do this |
    | --- | --- |
    | the pull request is a draft; mark it ready for review to run it | Mark it ready for review |
    | Stopped by … | Run `ssp resume` with the same target, or **Resume** in the dashboard |
    | a reviewer requested changes | Make the changes, and get a new review |
  </Accordion>

  <Accordion title="The commit has no build">
    The reason is `<commit> has no build yet`. CI did not record the head commit yet. Look at the `Statespace` check, and at the workflow run of the commit. If CI could not record the commit, the check failed and says why.
  </Accordion>

  <Accordion title="The base did not run as the default">
    The reason is `its base <commit> has not run as the default yet`. Deploy the default branch at that commit or later. Make sure that a proxy runs it. With continuous deployment, this takes some minutes at most.
  </Accordion>

  <Accordion title="Another arm of the experiment merged">
    The reason is `an arm of <experiment> merged; update this branch with the default branch`. The merge ended the experiment version. Update the branch with the default branch, and push.
  </Accordion>

  <Accordion title="The rules differ from the other arms">
    The reason is `its subject or eligibility rule differs from the other arms of <experiment>`. Use the same `subject` and `eligibility` in each arm of the experiment. To test another audience, use another experiment name.
  </Accordion>

  <Accordion title="The app has no free traffic">
    The reason is `experiments would hold X of the app's subjects, over its Y limit`. The arm waits until it fits, first come, first served. Lower its share, stop another arm, or raise `max_traffic` on the default branch.
  </Accordion>
</AccordionGroup>
