---
title: Analyze the outcomes
description: Query runs, outcomes, and host measurements, then record a decision.
---

Start with allocation and delivery checks. Then estimate the outcome for each variant within one experiment version.

Analysis runs against your own PostgreSQL database. Create a read-only credential for the app once and point any SQL client at it.

```shell
ssp database credential create --name analyst --app atlas
```

## Check assignment counts

Count runs by assignment reason.

```sql
SELECT reason, count(*)
FROM atlas.runs
WHERE experiment = 'rank-v2'
GROUP BY reason;
```

Check that subjects split as the weights say. `ssp experiment results` tests the split once 100 subjects ran.

```shell
ssp experiment results rank-v2 --outcome click | jq '.sample_ratio'
```

A `mismatch` means assignment or recording is broken, and the effects cannot be trusted. The most common cause is a variant that fails for some subjects. Each variant's `unavailable` count shows how many of its subjects control served.

## Check the variants' health

Compare errors and latency across processes before you trust outcomes.

```sql
SELECT variant,
       sum((data->>'requests')::int) AS requests,
       sum((data->>'errors')::int) AS errors,
       max((data->>'p90_ms')::double precision) AS worst_p90_ms
FROM atlas.metrics
WHERE kind = 'http' AND timestamp > now() - interval '1 day'
GROUP BY variant;
```

## Compare variants

List the outcomes the app recorded.

```shell
ssp app outcomes atlas
```

Count subjects in the variant they were assigned to, including runs that control served because the variant was unavailable. Leaving those runs out hides failures. Extract numeric values from the JSONB `data` column.

```sql
SELECT
  variant,
  count(*) AS observations,
  avg((data->>'position')::double precision) AS mean_position,
  stddev_samp((data->>'position')::double precision) AS sd_position
FROM atlas.logs
WHERE experiment = 'rank-v2'
  AND experiment_version = 1
  AND reason IN ('assigned', 'variant-unavailable')
  AND outcome_name = 'click'
GROUP BY variant;
```

Or summarize one outcome with the CLI.

```shell
ssp experiment results rank-v2 --outcome click --metric position
```

## Connect another tool

Create a read-only PostgreSQL credential for a BI tool, notebook, or coding agent. Omit `--app` to read every app.

```shell
ssp database credential create --name notebook
```

Revoke the credential when the integration no longer needs access.

```shell
ssp database credential revoke dbc_123
```

## Make a decision

Decide on the primary outcome you chose before the experiment, with its uncertainty. Then check every guardrail: a better primary outcome does not cancel harm to a guardrail. Finally, weigh the effect against the cost and risk of shipping it. A precise effect can still be too small to be worth it.

Choose one action:

- **Ship** when the benefit holds and the guardrails pass.
- **Reject** when the variant is not worth it.
- **Revise** when the evidence points to a fixable problem.
- **Repeat** with a confirmatory experiment when uncertainty is still material.

Record the decision as a note when you stop the experiment, where the next person or agent will look. Stopping sends every subject back to control and keeps the evidence queryable.

```shell
ssp experiment stop rank-v2 --note 'Ship: +1.8 points of click rate (+0.6 to +3.0), no latency change.'
```

Notes are kept with the experiment version and each variant's version and commit.

```sql
SELECT timestamp, action, note, variants FROM atlas.notes WHERE experiment = 'rank-v2';
```

To ship, merge the variant's branch and deploy it as usual; Statespace does not deploy control. Turn open questions into a new experiment rather than editing a finished one.
