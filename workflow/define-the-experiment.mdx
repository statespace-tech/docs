---
title: Define the experiment
description: Choose a subject key, eligibility rule, and published function.
---

Start with one decision. Choose the randomization unit, eligible population, candidate function, and outcome before you start.

## Choose the randomization unit

Use a stable identifier at the level where treatment can vary independently. Use `user_id` for individual users or `account_id` when users in one account can affect each other. The assignment label does not extract a context field. The application supplies its value to the SDK.

## Publish the candidate

Save the candidate as `rerank.py`.

```python
def rerank(items: list[int]) -> list[int]:
    return sorted(items)
```

Build its Wasm component and publish the immutable function `atlas-search@1`.

```shell
ssp function build rerank.py --language python --entry rerank:rerank --output rerank.wasm
ssp function publish rerank.wasm --name atlas-search
```

S3 stores the bytes. PostgreSQL stores the SHA-256 hash, object key, and publisher provenance. SDKs execute the component locally.

## Create the draft

Use a CEL rule with pre-treatment context and allocate 20% of eligible users to the candidate.

```shell
ssp experiment create --name rank-v2   --description 'Test sorted search results.'   --assignment user_id   --eligibility 'context.country == "US" && context.plan == "pro"'   --variant atlas-search@1=0.2
```

The remaining 80% uses the application's default callable as control. Ineligible subjects also use the default, but are logged as unassigned. The backend validates CEL before committing the draft.

Review version 1 before starting it.

```shell
ssp experiment show --name rank-v2
```

The CLI accepts flags directly. Updates supply a full replacement definition and create a new immutable draft. Omitted optional flags reset to defaults.
