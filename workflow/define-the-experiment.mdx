---
title: Define the experiment
description: Publish the variant, then choose its subjects, eligibility, and share of subjects.
---

Start with one decision. Choose the randomization unit, eligible population, variants, and outcome before you start.

## Choose the randomization unit

Use a stable identifier at the level where treatment can vary independently. Read it from the request with a CEL subject rule, such as `request.headers["x-user-id"]` for users or `request.headers["x-account-id"]` for accounts. Without a rule, each browser is a subject.

## Print the outcome

Statespace records each line that an arm prints, with its arm. Thus, your current logs are also evidence. Print a JSON line where the outcome occurs. To compare subjects, add a `subject` field.

```python
subject = request.headers["x-statespace-subject"]
print(json.dumps({"event": "click", "subject": subject, "position": position}))
```

The proxy calculates the subject with your subject rule. It sends the result in the `x-statespace-subject` header. The app reads the subject from this header.

Deploy this change to production first. Then the default and each variant print the same lines.

## Build the variant

Make one change on a branch. Build its image the way you build production.

```shell
git checkout new-ranking
docker build -t ghcr.io/acme/atlas:new-ranking .
```

Check that it starts and answers before you publish it.

```shell
docker run --rm -p 8000:8000 ghcr.io/acme/atlas:new-ranking
curl localhost:8000/search?q=maps
```

## Publish the variant

Push the image, then sign and publish it. In CI, the signing key comes from `SSP_SIGNING_KEY`.

```shell
docker push ghcr.io/acme/atlas:new-ranking
ssp variant create atlas-search --app atlas --image ghcr.io/acme/atlas:new-ranking
```

The CLI resolves the tag to the image's digest with `docker`. The variant records the digest, the commit, and the signature. Proxies and the controller run only variants signed by a key they trust.

## Create the draft

Give the variant 5% of the app's subjects. The control arm gets another 5%. State the hypothesis in a note.

```shell
ssp experiment create rank-v2 --app atlas --split atlas-search=0.05 \
  --subject 'request.headers["x-user-id"]' \
  --eligibility 'request.headers["cf-ipcountry"] == "US"' \
  --note 'Sorted results should get more clicks.'
```

Every other subject gets the default. The backend validates both CEL rules and checks that each variant exists before it saves the draft.

Review the draft before starting it. Its `split` shows each arm's share of all subjects.

```shell
ssp experiment show rank-v2
```

`ssp experiment update` changes the draft. Omitted flags keep their values, and `--split` replaces the draft's arms.
