The CLI can use a saved account session. CI and `ssp host` use `SSP_API_KEY`.
Bearer API keys require the route's scope. Browser sessions use cookies and the
configured frontend origin for mutations.

## Account routes

Use account routes to manage credentials, sessions, audit records, and storage.

```text
GET    /v1/account
GET    /v1/keys
POST   /v1/keys
DELETE /v1/keys/{id}
GET    /v1/tokens
DELETE /v1/tokens/{id}
POST   /v1/credentials/revoke-all
GET    /v1/database/credentials
POST   /v1/database/credentials
DELETE /v1/database/credentials/{id}
GET    /v1/audit
GET    /v1/storage
```

`/v1/audit` includes `source` and `occurred_at`. Use IDs with the `before` cursor
for pagination. Compare `occurred_at` for chronology; IDs combine independent
ledger counters.

There is no SQL query endpoint. Account database credentials provide read-only
access through your PostgreSQL client.

## Authentication routes

Sign in or sign up with a configured GitHub or Google provider.

```text
GET    /v1/auth/providers
GET    /v1/auth/web/{provider}/start
GET    /v1/auth/github/callback
GET    /v1/auth/google/callback
GET    /v1/auth/session
DELETE /v1/auth/session
POST   /v1/auth/device
POST   /v1/auth/device/approve
POST   /v1/auth/device/token
```

Provider clients must be registered with the exact callback URLs. Device
approval requires a signed-in user. Callback state and device redemption are
single use.

## App, variant, and experiment routes

Manage apps, variants, and experiments with an `experiments:write` key or a session.

```text
GET    /v1/apps
POST   /v1/apps
GET    /v1/apps/{app}
PATCH  /v1/apps/{app}
DELETE /v1/apps/{app}
POST   /v1/apps/{app}/bundles
GET    /v1/apps/{app}/variants
POST   /v1/apps/{app}/variants
GET    /v1/apps/{app}/variants/{name}
DELETE /v1/apps/{app}/variants/{name}
GET    /v1/apps/{app}/variants/{name}/logs?limit={n}&version={n}
GET    /v1/apps/{app}/hosts
DELETE /v1/apps/{app}/subjects/{subject}
GET    /v1/experiments?app={app}
POST   /v1/experiments
GET    /v1/experiments/{name}
PATCH  /v1/experiments/{name}
DELETE /v1/experiments/{name}
POST   /v1/experiments/{name}/start
POST   /v1/experiments/{name}/stop
GET    /v1/experiments/{name}/results?outcome={name}&metric={field}&version={n}
```

`POST /v1/apps/{app}/bundles` takes a bundle's SHA-256 and size. It returns a short-lived S3 URL and the headers to `PUT` the bytes with, or `"exists": true` when the bundle is stored. S3 rejects bytes that do not match the SHA-256.

```json
{ "sha256": "3fa9…", "size": 48213 }
```

`POST /v1/apps/{app}/variants` publishes the next version of a variant from an uploaded bundle. The service checks the signature to catch mistakes; hosts decide which keys they trust.

```json
{
  "name": "atlas-search",
  "sha256": "3fa9…",
  "command": null,
  "commit": "4f2a9c1",
  "signature": "Jx0b…",
  "public_key": "q8Lm…"
}
```

An experiment maps variant names to weights.

```json
{
  "name": "rank-v2",
  "app": "atlas",
  "variants": { "atlas-search": 0.5 },
  "traffic": 0.2,
  "subject": "request.headers[\"x-user-id\"]",
  "eligibility": "request.headers[\"cf-ipcountry\"] == \"US\"",
  "note": "Sorted results should get more clicks."
}
```

`PATCH /v1/experiments/{name}` changes the draft. `POST /start` publishes it and accepts an optional `{"version": 1}` to restart a published version instead. `start`, `stop`, and `PATCH` accept a `note`.

## Host routes

Read the app's running configuration and bundles, report capacity, and submit events. These routes need a `runtime:read` and `events:write` key.

```text
GET  /v1/runtime/apps/{app}
GET  /v1/runtime/apps/{app}/bundles/{sha256}
POST /v1/runtime/apps/{app}/hosts
POST /v1/events
```

The configuration lists every running experiment with its slice of the app's traffic, its rules, and each variant's ranges, bundle, command, commit, and signature. Hosts poll it every 10 seconds. A bundle route returns a short-lived download URL.

A host report sets the host's capacity. `start` fails when the hosts that reported in the last three minutes cannot run the variants that running experiments would need.

```json
{ "id": "web-1-a3f2c1", "max_variants": 4, "report": { "processes": [] } }
```

The batch endpoint accepts up to 1,000 events of one app in one request. An outcome names its subject, not an experiment or a run.

```json
{
  "app": "atlas",
  "runs": [{ "id": "run_1", "experiment": "rank-v2", "version": 1, "subject_id": "u_42",
             "variant": "atlas-search", "variant_version": 3, "reason": "assigned",
             "context": { "method": "GET", "path": "/search" } }],
  "outcomes": [{ "id": "out_1", "subject_id": "u_42", "name": "click",
                 "data": { "position": 1 }, "variant": "atlas-search", "variant_version": 3 }],
  "requests": [],
  "output": [],
  "metrics": [],
  "lifecycle": []
}
```

`202 Accepted` means the account outbox has committed the events. The worker
retries SQS delivery and writes the final rows. Duplicate queue delivery is
idempotent. Each serialized event is limited to 64 KiB. Raw events expire after
90 days, and captured output after its app's output retention. The event quota is 1 GiB on the free plan and 10 GiB on other plans, including pending events.

## Errors

Errors use one JSON object and an HTTP error status.

```json
{
  "error": "bad request: event exceeds 64 KiB"
}
```
