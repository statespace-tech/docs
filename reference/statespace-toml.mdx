`statespace.toml` holds the settings, events, and metrics of the apps that run from its folder. It has no app name: the name comes from `ssp app add` and `ssp proxy --app`.

```toml statespace.toml
# Shared settings for every app built from this folder.
subject = 'request.cookies.ssp_sid'
eligibility = 'request.headers["cf-ipcountry"] == "US"'
max_traffic = 0.2
max_arms = 5
arm_role = "write"
overrides = false
redact = ['\b\d{16}\b']

[[event]]
name = "checkout"
match = '''
request.method == "POST"
  && request.path == "/api/checkout"
  && request.status < 300
'''

[[event]]
name = "fatal"
match = 'stderr.text.contains("FATAL")'

[[metric]]
label = "checkout rate %"
value = '100.0 * events["checkout"].subjects / subjects'

# Per-app sections change and extend the shared settings.
[app.shop-dev]
max_traffic = 1.0
overrides = true

[app.shop-prod]
arm_role = "maintain"
```

## Settings

<ParamField path="subject" type="CEL → string" default="request.cookies.ssp_sid">
  The subject ID of a request. When the expression gives no string, the request goes to live. See [Subjects](/concepts/subjects).
</ParamField>

<ParamField path="eligibility" type="CEL → bool" default="everyone">
  Who can be in the control or an arm. An error sends the request to live, with the reason `eligibility-error`.
</ParamField>

<ParamField path="max_traffic" type="number" default="0.2">
  The largest share of subjects in all arms and the control together. From more than 0 to 1.
</ParamField>

<ParamField path="max_arms" type="integer" default="5">
  The most arms that run at the same time. The control does not count. 1 or more.
</ParamField>

<ParamField path="arm_role" type="string" default="write">
  The level that adds and removes arms of the app: `write`, `maintain`, or `admin`. See [Permissions](/concepts/permissions).
</ParamField>

<ParamField path="overrides" type="boolean" default="false">
  Let testers open a running arm. See [Overrides](/concepts/overrides).
</ParamField>

<ParamField path="redact" type="string[]">
  Regular expressions. The proxy replaces their matches in output lines with `[redacted]` before the lines leave the machine.
</ParamField>

`subject` and `eligibility` use `request` with `method`, `path`, `query`, `headers`, and `cookies`. See [CEL variables](/reference/cel).

## Events

Each `[[event]]` defines a named count. See [Events and metrics](/concepts/events-and-metrics).

<ParamField path="name" type="string" required>
  The name of the event, such as `checkout`. Metrics use it in `events["checkout"]`.
</ParamField>

<ParamField path="match" type="CEL → bool" required>
  The rule. It uses exactly one source: `request`, `stdout`, or `stderr`.
</ParamField>

## Metrics

Each `[[metric]]` is a formula over the totals of one side. The first metric is the headline.

<ParamField path="label" type="string" required>
  The name that the evidence shows, such as `checkout rate %`.
</ParamField>

<ParamField path="value" type="CEL → number" required>
  The formula. See [CEL variables](/reference/cel#metric-value).
</ParamField>

## Per-app sections

A section `[app.<name>]` holds settings for one app.

- A key in the section replaces the shared key.
- `[[app.<name>.event]]` and `[[app.<name>.metric]]` are added after the shared events and metrics.
- A section that matches no app gives a warning in CI. It is not an error.

## When a change takes effect

1. You commit a change to `statespace.toml`.
2. CI records the build of the commit. Statespace checks the file. A wrong key, a wrong type, or a CEL error fails the CI step.
3. The commit runs as live.
4. The app gets the settings of the file in the build of its live commit.
5. Each arm of the app starts a new version.
