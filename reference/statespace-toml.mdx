`statespace.toml` holds the events and experiments of the apps that run from its folder. It has no app name: the name comes from `ssp app add` and the runtime token of the proxy. Several apps can run from one folder, such as `shop-dev` and `shop-prod`.

## Starter file

Write this file in the folder of your app's code. A person or a coding agent can copy it. Change the event to a route of your app.

<StarterToml />

## Full example

```toml statespace.toml
# Shared events: in every experiment.
[[event]]
name = "purchase"
match = '''
request.method == "POST"
  && request.path == "/checkout"
  && response.status < 300
'''

# Experiments, in priority order.
[experiment.checkout]
subject = 'request.headers["x-user-id"]'
max_traffic = 0.2

[[experiment.checkout.event]]
name = "coupon"
match = '''
request.method == "POST"
  && request.path == "/checkout/coupon"
'''

[experiment.us-landing]
eligibility = 'request.headers["cf-ipcountry"] == "US"'
max_traffic = 0.15

# Per-app sections replace and extend the shared settings.
[app.shop-dev.experiment.checkout]
max_traffic = 1.0
```

## Settings

<ParamField path="[[event]]" type="table">
  A shared event, with `name` and `match`. It applies to every experiment. See [Events](#events).
</ParamField>

<ParamField path="[experiment.<name>]" type="table">
  One experiment. See [Experiments](#experiments).
</ParamField>

<ParamField path="[app.<name>]" type="table">
  Settings for one app. See [Per-app sections](#per-app-sections).
</ParamField>

## Experiments

Each table `[experiment.<name>]` defines one experiment. An empty table is an experiment with the defaults. You set its arms with [`ssp experiment update`](/reference/cli#ssp-experiment-update).

<ParamField path="subject" type="CEL → string" default="request.cookies.ssp_sid">
  The subject ID of a request. When the expression gives no string, the experiment skips the request. See [Subjects](/concepts/subjects).
</ParamField>

<ParamField path="eligibility" type="CEL → bool" default="everyone">
  Who can enter the experiment. When the expression is false or has an error, the experiment skips the request.
</ParamField>

<ParamField path="max_traffic" type="number" default="0.2">
  The largest total of the shares of the experiment's arms. A fraction: more than 0, and 1 at most.
</ParamField>

<ParamField path="[[experiment.<name>.event]]" type="table">
  An own event of the experiment, with `name` and `match`. It applies only to this experiment.
</ParamField>

- A name has 1 to 40 characters: lowercase letters, digits, and `-`.
- Each experiment exists in every app of the folder. Its arms and its state are different for each app.
- `subject` and `eligibility` use `request` with `method`, `host`, `path`, `query`, `headers`, and `cookies`. They run before the response exists, so they cannot use `response`. See [CEL variables](/reference/cel).

### Priority order

The order of the `[experiment.*]` tables is the priority order. When two running experiments can claim the same request, the experiment that is first in the file gets it. In the full example, `checkout` comes before `us-landing`. See [Assignment](/concepts/subjects#assignment).

## Events

<Planned />

Each event defines a named count. See [Events](/concepts/events).

<ParamField path="name" type="string" required>
  The name of the event, such as `purchase` or `add_to_cart`. The results show it as `purchase %`. A name is lowercase snake_case: a lowercase letter, then lowercase letters, digits, or `_`, at most 64 characters.
</ParamField>

<ParamField path="match" type="CEL → bool" required>
  The rule, over one request and its response. It can use `request` and `response`. See [CEL variables](/reference/cel#event-match).
</ParamField>

## Shared and own

- Shared events apply to every experiment.
- Own events of an experiment come after the shared ones, and apply only to it.
- The same event name two times is an error in CI: `event "coupon" is defined twice`.
- The results show one row for each event, in this order.
- The **headline** is the first event of the experiment, shared events first. When the experiment has no events, the headline is the error rate.

## Per-app sections

A section `[app.<name>]` holds settings for one app. It can hold:

- `[[app.<name>.event]]`. They are added after the shared events.
- `[app.<name>.experiment.<exp>]`, with experiment keys. They replace the shared keys of that experiment for that app.

A section that matches no app gives a warning in CI. It is not an error.

## When a change takes effect

1. You commit a change to `statespace.toml`.
2. CI records the build of the commit. Statespace checks the file. A wrong key, a wrong type, or a CEL error fails the CI step, with the message. For example, `subject` at the top level is a wrong key: it belongs in an `[experiment.<name>]` table.
3. The commit runs as live.
4. The app gets the settings and experiments of the file in the build of its live commit.

## What a release does to a running experiment

| The release changes | Result |
| --- | --- |
| Only code | Nothing. `ssp experiment show` says "live is now f2f2f2f" |
| `subject`, `eligibility`, or `max_traffic` of the experiment, or removes its table | The experiment stops |
| A shared event | Every running experiment of the app stops |
| An own event of the experiment | The experiment stops |

The note of the stop is "definition changed in live d00d123". `ssp experiment show`, the commit statuses, and the audit log give it, with the start command to run again. See [What a release does](/concepts/experiments#what-a-release-does).
